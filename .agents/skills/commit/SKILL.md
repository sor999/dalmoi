# 커밋 단위

- 변경 이력을 기능별로 추적할 수 있도록 개발한 기능 또는 독립적인 변경 목적 단위로 커밋을 나눔
- 서로 다른 기능, 버그 수정, 리팩터링 및 설정 변경을 관련 없이 하나의 커밋에 묶지 않음
- 하나의 기능을 완성하는 구현, 관련 테스트 및 필요한 문서는 같은 커밋에 포함할 수 있음
- 파일 개수나 계층별로 기계적으로 나누지 않고, 각 커밋의 목적과 변경 이유를 독립적으로 이해할 수 있는 단위로 구성
- 각 커밋은 가능한 한 빌드와 관련 테스트가 통과하는 완결된 상태를 유지하고, 의존하는 변경부터 순서대로 커밋
- 커밋 전 전체 변경사항을 확인하고 해당 기능에 필요한 파일과 변경 부분만 선택적으로 스테이징하여 무관한 변경이 섞이지 않도록 확인

# 커밋 전 컨벤션 확인

- 에이전트는 코드·빌드·검사 설정을 커밋하기 전에 다음 절차를 직접 수행한다. 훅이 설치되어 있거나 CI가 예정되어 있다는 이유로 생략하지 않는다.
- 변경 영역의 AGENTS.md와 코드·테스트 컨벤션을 확인하고 필드 애너테이션 위치, 선언 사이 빈 줄, 불필요한 줄바꿈 및 의미 단위별 본문 구분을 검토한다. Java/Spring 전용 규칙을 Kotlin에 그대로 적용하지 않는다.
- 백엔드 변경은 `backend/`에서 `./gradlew spotlessApply` 실행 후 `./gradlew spotlessCheck checkstyleMain checkstyleTest`를 통과시킨다.
- Android 변경은 `android/`에서 `./gradlew spotlessApply` 실행 후 `./gradlew spotlessCheck androidLint`를 실행한다. 앱 모듈이 없어 Android Lint가 SKIPPED되면 형식 검사 통과와 Lint 미실행을 구분해 보고한다.
- 양쪽을 변경하면 각각 검사한다. 문서만 변경한 경우에는 문서 내용과 링크 및 `git diff --check`를 확인하며 불필요한 Gradle 실행은 하지 않는다.
- 자동 포맷 결과에서 요청 범위 밖의 변경이 생겼는지 확인하고, 해당 기능에 필요한 파일·부분만 선택적으로 스테이징한다. 사용자의 다른 변경이나 기존 스테이징 상태를 임의로 덮어쓰지 않는다.
- 최종 스테이징 후 `git diff --cached --check`와 `git diff --cached`로 커밋 내용을 재확인한다. 검사 후 코드를 다시 수정하면 영향을 받는 검사를 재실행한다.
- 훅 설치 상태를 확인하고, 설치되지 않았다면 저장소의 설치 스크립트를 사용한다. 기존의 다른 훅 경로가 있으면 임의로 덮어쓰지 않고 확인한 상태를 보고한다.
- 검사 실패를 해결하지 못하면 커밋하지 않고 원인과 미검증 범위를 보고한다. `--no-verify`나 검사 규칙 완화로 우회하지 않는다.

# 커밋 작성

- 커밋 메시지는 `타입: 변경 요약` 형식 사용
- 제목 아래 빈 줄을 두고 변경 내용과 이유를 개조식 본문으로 작성
- 상세 설명 본문은 제목을 제외하고 공백과 줄바꿈을 포함해 총 100자 이내로 작성
- 이슈 참조 문구(`Refs #번호` 등)는 작성하지 않음
- 변경 성격에 맞는 타입 사용: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `style`, `perf`, `build`, `ci`, `revert`
- 예시: `feat: 주문 생성 기능 추가`
- 타입 뒤 괄호 사용 금지: `feat(주문): ...` 형식 사용 금지

# 어투

- 변경 내용을 간결한 개조식 및 명사형으로 작성
- 목록 사용 시 하이픈으로 통일하고 중단점(·) 혼용 금지

# 에이전트 표기 금지

- 제목과 본문에 에이전트가 작성하거나 커밋했다는 문구 추가 금지
- 에이전트 이름, AI 생성 문구 및 에이전트 공동 작성자 표기(`Co-authored-by`) 추가 금지
