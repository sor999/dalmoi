# 체크아웃 규칙

- 기존 브랜치 규칙이 있으면 우선 따르고, 별도 규칙이 없으면 작업 브랜치는 `feature/이슈번호-동사-기능` 형식 사용
- 예시: `feature/123-create-order`
- 현재 브랜치와 작업 트리를 먼저 확인하고, 이슈가 있으면 기존 번호 사용
- 이슈 초안은 `../issue/SKILL.md`를 참고하며 요청 없이 이슈를 자동 생성하지 않음
- 이슈가 없으면 번호를 만들지 않고 저장소 규칙에 맞는 설명형 브랜치명 사용
- 브랜치 생성 및 체크아웃은 요청된 작업 범위에서 수행하고 기존 변경사항 보존

# 머지 이후 새 작업 브랜치

- PR이 머지된 소스 브랜치는 이후 작업이나 새 PR에 재사용하지 않음. 스쿼시 머지된 브랜치에도 동일하게 적용
- 새 작업은 최신 대상 브랜치를 동기화한 뒤 그 기준에서 새 브랜치로 시작하며, 머지된 브랜치의 이름만 바꿔 기존 커밋을 이어 사용하지 않음
- 같은 이슈 번호를 계속 사용해도 브랜치 이름은 새 작업 목적에 맞게 변경. 예: `feature/123-create-order` 머지 후 `feature/123-fix-order-validation` 생성
- 같은 작업 설명이 필요하면 `feature/123-create-order-followup-2`처럼 구분 가능한 접미사를 붙이고, 이미 머지된 브랜치 이름을 다시 사용하지 않음
- 기존 브랜치의 머지 여부는 GitHub PR 이력으로 확인. 스쿼시 머지는 원래 커밋의 조상 관계가 남지 않을 수 있으므로 로컬 커밋 포함 여부만으로 미머지라고 판단하지 않음

프로젝트 PR 템플릿 기반 작성 지침

# PR 작성

- Git 저장소 루트의 `.github/pull_request_template.md` 또는 `.github/PULL_REQUEST_TEMPLATE/`에 템플릿이 있으면 활용 및 기존 구조 유지
- 템플릿이 없으면 관련 이슈·변경 내용·검증 결과·참고 사항으로 작성
- PR 생성과 push는 사용자 요청 범위에서 수행
- 제목은 `타입: 작업 요약` 형식 및 타입 뒤 괄호 금지
- `📌 관련 이슈`: 실제로 연관되고 이 PR로 해결하는 이슈가 있을 때 `closes #이슈번호` 작성
- `✨ 변경 내용`: 변경 요약과 배경 작성, 보충 내용은 H3(`###`)로 구분
- `📎 참고 사항`: 다른 팀원이 작업하거나 리뷰·배포를 판단할 때 반드시 알아야 하는 내용만 작성

# 참고 사항 작성 기준

- 팀원의 행동이나 판단에 영향을 주는 내용으로 제한: 필수 환경변수·설정 변경, 마이그레이션 및 배포 순서, API 호환성 영향, 선행 PR 의존성, 알려진 제약이나 미해결 문제
- 관련 문서와 후속 작업도 팀원이 반드시 확인하거나 수행해야 하는 경우에만 포함
- 변경 내용의 반복, 일반적인 테스트 성공 기록·실행 명령, 라벨 같은 관리 정보, 에이전트의 작업 과정 및 관례적인 안내는 제외
- 검증 실패나 미검증 범위가 팀원의 판단에 영향을 주면 원인과 실제 영향을 간결하게 명시
- 반드시 전달할 내용이 없으면 억지로 항목을 채우지 않고 비워 둠

# 라벨

- Android 변경사항이 있는 PR에는 `and` 라벨 적용
- 백엔드 변경사항이 있는 PR에는 `be` 라벨 적용
- Android와 백엔드 변경사항이 함께 있으면 두 라벨 모두 적용
- 기술별 지침과 컨벤션 문서 변경도 해당 영역에 포함하며, 공통 변경만 있는 경우 두 라벨을 임의 적용하지 않음
- PR 초안에는 적용할 라벨을 명시하고, PR 생성 및 수정 시 실제 라벨에 반영

# 어투

- 간결한 개조식 및 명사형 종결 사용
- 목록은 하이픈 또는 체크박스로 통일하고 중단점(·) 혼용 금지
