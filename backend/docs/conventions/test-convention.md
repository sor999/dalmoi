# Spring Boot 테스트 컨벤션

## 1. 목적

Spring Boot 백엔드의 테스트 작성 기준을 정의한다.

테스트는 가장 작은 적절한 범위에서 작성하되, 실제 DB 동작이 필요한 기능은 운영 DB와 같은 엔진의 Testcontainers 또는 기존 테스트 인프라로 검증한다.

테스트 통과 자체보다 비즈니스 요구사항, 데이터 정합성 및 테스트 신뢰성을 보장하는 것을 우선한다.

## 2. 테스트 기술 스택

- Java와 Spring Boot 버전은 빌드 파일 및 toolchain을 기준으로 확인한다.
- JUnit, AssertJ, Mockito, MockMvc는 프로젝트에서 지원하는 버전을 사용한다.
- 운영 DB 엔진과 버전은 애플리케이션 설정, 컨테이너 구성 및 배포 설정으로 확인한다.
- Testcontainers는 실제 DB 동작 검증이 필요할 때 사용하며 기존 인프라를 우선한다.
- Gradle 또는 Maven은 저장소의 빌드 도구와 wrapper를 사용한다.

프로젝트에 이미 정의된 테스트 의존성과 설정을 우선 사용한다. 아래 컨벤션은 별도 팀 규칙이 없을 때의 기본안이며, 프로젝트 버전에 맞는 애너테이션과 API를 사용한다.

## 3. 공통 컨벤션

### 테스트 네이밍

- 테스트 클래스명은 `{대상클래스}Test`를 기본으로 사용한다.
- 모든 `@Test`, `@ParameterizedTest`, `@RepeatedTest` 메서드에 `@DisplayName`을 작성한다.
- 테스트 메서드명은 영어로 작성하며 검증 대상과 기대 결과를 명확하게 표현한다.
- `@DisplayName`은 자연스러운 한국어로 조건과 기대 결과를 작성한다.
- `@Nested` 사용 시 중첩 클래스에도 `@DisplayName`을 작성한다.
- 파라미터화 테스트는 `@ParameterizedTest(name = "...")`로 각 실행 케이스를 구분한다.
- 기존 테스트에 `@DisplayName`이 없다면 관련 기능 수정 시 함께 보완한다.

### 테스트 구조

- Arrange, Act, Assert 흐름을 유지한다.
- Given-When-Then 주석은 필요한 경우에만 작성한다.
- 테스트는 서로 독립적으로 실행할 수 있어야 한다.
- 테스트 실행 순서와 공유 상태에 의존하지 않는다.
- 기존 Fixture와 테스트 유틸리티를 우선 재사용한다.
- `var`보다 명시적인 타입 선언을 우선한다.

### 검증 원칙

- AssertJ를 기본 Assertion 라이브러리로 사용한다.
- 정상 동작뿐 아니라 중요한 실패 경로도 검증한다.
- 반환값, 예외, 상태 변경 및 최종 데이터 상태를 명확하게 검증한다.
- 단순히 예외 없이 실행되는지만 확인하는 테스트를 지양한다.
- Mockito의 `verify()`는 중요한 의존성 호출을 확인해야 할 때 사용한다.
- Mock 호출 여부만으로 비즈니스 로직의 정상 동작을 검증했다고 판단하지 않는다.
- 테스트를 통과시키기 위해 기대값이나 검증 조건을 임의로 완화하지 않는다.

## 4. 테스트 유형별 컨벤션

### Entity 및 순수 단위 테스트

- Entity의 상태 변경, 값 객체, 계산 로직은 Spring 컨텍스트 없이 테스트한다.
- 실제 도메인 메서드를 호출하여 상태 전이를 검증한다.
- 외부 의존성이 없는 로직에 불필요한 Mock을 사용하지 않는다.
- 유효하지 않은 상태 전이나 비즈니스 규칙 위반을 검증한다.

### Mockito Service 단위 테스트

- Spring 컨텍스트가 필요하지 않다면 `@ExtendWith(MockitoExtension.class)`를 사용한다.
- 의존성은 `@Mock`, 테스트 대상은 `@InjectMocks`로 구성한다.
- 서비스의 조건 분기, 권한 검사, 예외 처리 및 중요한 협력 객체 호출을 검증한다.
- 실제 DB의 트랜잭션이나 제약조건에 의존하는 동작을 Mock만으로 검증하지 않는다.
- 최소한의 Mock과 Stubbing을 사용한다.

### Controller 테스트

- `@WebMvcTest`와 MockMvc를 사용한다.
- Service 의존성은 프로젝트 버전에서 지원하는 테스트 Mock 애너테이션(예: `@MockitoBean`)으로 대체한다.
- 요청 DTO 바인딩, Jakarta Validation 및 HTTP 상태 코드를 검증한다.
- 응답 본문과 주요 필드가 올바르게 반환되는지 확인한다.
- 인증되지 않은 요청과 권한 관련 응답을 검증한다.
- 잘못된 PathVariable, RequestParam 및 RequestBody를 확인한다.
- Controller 테스트에 불필요한 PostgreSQL Testcontainers를 실행하지 않는다.
- 비즈니스 로직 자체의 검증은 Service 테스트에서 수행한다.

### Service 통합 테스트

- 트랜잭션, JPA 영속성 컨텍스트, 여러 Repository 간 협력이나 DB 제약조건이 중요하면 통합 테스트를 작성한다.
- 프로젝트의 기존 DB 통합 테스트 애너테이션과 지원 설정을 우선 사용한다.
- 일반 통합 테스트에는 `@Transactional`을 적용하여 테스트 후 롤백한다.
- 테스트에 필요한 데이터를 기존 Fixture를 활용해 준비한다.
- 서비스 실행 후 반환값뿐 아니라 실제 데이터 상태도 검증한다.
- DB 반영 여부가 중요하다면 `flush()`와 `clear()`를 활용한다.
- 단위 테스트로 충분한 로직에 불필요한 전체 Spring 컨텍스트를 실행하지 않는다.

### Repository 통합 테스트

- JPA 매핑, JPQL, QueryDSL, Native Query 검증에는 `@DataJpaTest`를 우선 사용한다.
- 운영 DB와 같은 엔진 및 호환 버전의 Testcontainers 또는 기존 테스트 인프라를 활용한다.
- `@AutoConfigureTestDatabase(replace = Replace.NONE)`을 사용하여 내장 DB 대체를 방지한다.
- 필요한 QueryDSL 및 JPA 설정을 기존 테스트 구성에서 재사용한다.
- 쿼리의 필터링, 정렬, 페이징 및 반환값을 검증한다.
- DB 제약조건의 예외 발생 여부를 검증할 때 `flush()`까지 실행한다.
- 영속성 컨텍스트의 캐시가 검증 결과에 영향을 주지 않도록 필요 시 `flush()`와 `clear()`를 호출한다.

## 5. 실제 DB 및 마이그레이션

- DB 고유 동작은 운영과 같은 DB 엔진 및 호환 버전으로 검증한다. PostgreSQL을 사용한다면 해당 버전의 PostgreSQL 컨테이너를 사용한다.
- Flyway나 Liquibase 등 마이그레이션 도구가 있다면 해당 마이그레이션을 테스트 DB 스키마의 기준으로 사용한다.
- 마이그레이션으로 스키마를 관리하는 JPA 테스트는 기존 검증 설정(예: `spring.jpa.hibernate.ddl-auto=validate`)을 유지한다.
- 테스트를 통과시키기 위해 `create`, `create-drop`으로 변경하거나 기존 마이그레이션 도구를 비활성화하지 않는다.
- FK, UNIQUE, CHECK, CASCADE 등 DB 제약조건을 검증한다.
- H2 등 대체 DB를 운영 DB 전용 쿼리, 인덱스, 제약조건 및 락 동작 검증의 최종 근거로 사용하지 않는다.
- Testcontainers가 동적으로 할당하는 포트를 사용하고 불필요한 고정 DB 포트를 설정하지 않는다.

## 6. 동시성 테스트

- 실제로 서로 다른 스레드와 독립된 트랜잭션에서 요청을 실행한다.
- 동시성 테스트 클래스에는 원칙적으로 `@Transactional`을 적용하지 않는다.
- `CountDownLatch` 등을 활용하여 동시 요청의 시작 시점을 조율한다.
- 단순 스레드 시작만으로 실제 DB 락 경합이 발생했다고 판단하지 않는다.
- 락 획득 및 대기 동작 자체가 검증 대상인 경우 실제 락 경합 상태를 확인한다.
- 요청별 성공과 실패 결과를 확인한다.
- 최종 DB 상태, 생성된 행 개수 및 비즈니스 불변식을 검증한다.
- `Thread.sleep()` 등 실행 타이밍에 의존하는 테스트를 지양한다.
- 예외를 무조건 무시하거나 성공 결과로 처리하지 않는다.
- 데이터 정리는 `@Sql` 등 명시적인 방법을 사용하되 다른 테스트 데이터에 영향을 주지 않도록 한다.

## 7. Fixture 컨벤션

- 프로젝트 테스트 소스의 기존 Fixture를 우선 재사용한다.
- Fixture 메서드명은 생성되는 객체와 상태를 명확하게 표현한다.
- 실제 DB에 저장하는 엔티티의 유니크 필드는 UUID 등을 사용해 충돌을 방지한다.
- 검증에 중요한 값은 Fixture 내부에 숨기지 않고 인자로 전달한다.
- 상태 전이는 리플렉션보다 실제 도메인 메서드를 우선한다.
- 공통 Fixture는 여러 테스트에서 반복적으로 사용되는 경우에만 추가한다.
- ID를 임의로 주입한 단위 테스트용 엔티티를 실제 DB에 저장하지 않는다.

## 8. 외부 인프라 테스트

- S3 등 실제 외부 서비스에 의존하는 테스트는 기본 테스트와 분리한다.
- 실제 외부 연동 테스트는 환경 변수 등을 이용한 Opt-in 방식으로 실행한다.
- 운영 리소스 대신 테스트 전용 리소스를 사용한다.
- 생성된 외부 리소스는 테스트 종료 시 반드시 정리한다.
- 외부 서비스 자격 증명과 비밀키를 코드 및 문서에 기록하지 않는다.
- 외부 환경 문제로 테스트가 실행되지 않은 경우 미검증 사항을 명시한다.
- 외부 연동 테스트가 의도적으로 건너뛰어진 경우 일반 테스트 실패로 판단하지 않는다.

## 9. 테스트 품질 및 유지보수

- 구현 세부사항보다 외부에서 관찰할 수 있는 동작을 검증한다.
- 테스트 하나는 가능한 한 명확한 검증 목적을 가진다.
- 동일한 기능을 중복으로 검증하는 테스트를 불필요하게 추가하지 않는다.
- 테스트 데이터와 기대 결과는 이해하기 쉽게 작성한다.
- 실패 시 어떤 요구사항을 만족하지 못했는지 파악할 수 있어야 한다.
- 테스트 코드에도 프로젝트의 네이밍 및 코드 스타일을 적용한다.
- 프로덕션 코드의 결함을 테스트 조건 수정으로 숨기지 않는다.
- 테스트 실패 원인이 코드, 환경, 데이터 또는 테스트 자체의 문제인지 구분한다.
